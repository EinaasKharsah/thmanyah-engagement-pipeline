# خط أنابيب تفاعل Thmanyah — نموذج محلي لمعالجة البيانات المتدفقة

## مقدمة

هذا المشروع يقدم **خط أنابيب بيانات متدفق (Streaming Pipeline)** يعمل محلياً لمعالجة أحداث التفاعل مع المحتوى. الهدف هو بناء نظام عملي وواضح يوضح كيفية استيعاب البيانات، إثرائها، تحويلها، وتوزيعها إلى عدة وجهات مختلفة.

المشروع مصمم ليكون **قابلاً للتكرار بالكامل** عبر Docker Compose، مما يجعله مثالاً واضحاً على كيفية بناء أنظمة معالجة البيانات في بيئة محلية بدون الحاجة إلى خدمات سحابية معقدة.

---

## فكرة المشروع باختصار

يبدأ المشروع بأحداث تفاعل بسيطة (مثل: مستخدم شاهد محتوى لمدة معينة) تُكتب في قاعدة بيانات PostgreSQL. ثم يتم نشر هذه الأحداث إلى Kafka، حيث يقوم معالج Stream Processing بإثراء كل حدث ببيانات إضافية من جدول المحتوى، يحسب مقاييس التفاعل، ويوزع النتائج إلى ثلاث وجهات:

- **ClickHouse**: لتخزين البيانات التحليلية
- **Redis**: لتجميع المحتوى الأكثر تفاعلاً في آخر 10 دقائق
- **External API**: لإرسال البيانات إلى أنظمة خارجية

---

## نظرة عامة على المعمارية

المشروع يتبع نمط **Streaming Pipeline** الكلاسيكي: البيانات تتدفق من المصدر عبر Kafka إلى المعالج، ثم تُوزع إلى عدة وجهات (Fan-out).

```
PostgreSQL → Kafka → Processor
                        ↘ ClickHouse
                        ↘ Redis
                        ↘ External API
```

### المكونات الرئيسية:

- **Generator**: يولد بيانات تجريبية ويكتبها في PostgreSQL
- **Publisher**: يقرأ الأحداث الجديدة من PostgreSQL وينشرها إلى Kafka (محاكاة Change Data Capture)
- **Processor**: يستخدم Faust لمعالجة الأحداث من Kafka، إثرائها، وتحويلها
- **Sinks**: ثلاث وجهات تستقبل البيانات المعالجة

---

## مصدر البيانات (Source Data)

### جدول المحتوى (`content`)

يحتوي على معلومات عن المحتوى المتاح في المنصة:
- معرف فريد (UUID)
- نوع المحتوى (فيديو، مقال، بودكاست، إلخ)
- مدة المحتوى بالثواني
- عنوان المحتوى
- تاريخ الإنشاء

هذا الجدول يمثل **الكاتلوج** الثابت للمحتوى.

### جدول أحداث التفاعل (`engagement_events`)

يسجل كل تفاعل بين مستخدم ومحتوى:
- معرف فريد للحدث (UUID)
- معرف المستخدم
- معرف المحتوى (يربط بالجدول `content`)
- مدة التفاعل بالميلي ثانية (قد تكون NULL)
- وقت الحدث

هذا الجدول يمثل **البيانات الأولية** التي تحتاج إلى معالجة وإثراء.

---

## الإثراء والتحويل (Enrichment & Transformation)

### الإثراء (Enrichment)

لكل حدث تفاعل، يقوم المعالج بـ:
- البحث في جدول `content` باستخدام `content_id`
- إضافة `content_type` (نوع المحتوى)
- إضافة `length_seconds` (مدة المحتوى)

إذا لم يُعثر على المحتوى، تُترك القيم كـ NULL.

### التحويل (Transformation)

يتم حساب مقاييسين رئيسيين:

**1. `engagement_seconds`**:
- تحويل `duration_ms` إلى ثواني (القسمة على 1000)
- إذا كانت `duration_ms` NULL، تكون النتيجة NULL

**2. `engagement_pct`**:
- نسبة التفاعل = `engagement_seconds` مقسومة على `length_seconds`
- يتم التقريب إلى رقمين عشريين
- إذا كانت `duration_ms` أو `length_seconds` NULL، تكون النتيجة NULL

هذه القواعد تضمن معالجة صحيحة للقيم المفقودة وتجنب الأخطاء الحسابية.

---

## توزيع النتائج إلى ثلاث وجهات (Multi-Sink Fan-out)

بعد الإثراء والتحويل، يتم إرسال كل حدث معالج إلى ثلاث وجهات مختلفة:

### 1. ClickHouse — التخزين التحليلي

- **الغرض**: تخزين جميع الأحداث المعالجة للتحليل اللاحق
- **الاستخدام**: استعلامات تحليلية مثل "أكثر أنواع المحتوى تفاعلاً" أو "متوسط نسبة التفاعل حسب النوع"
- **الخصائص**: محرك عمودي سريع مناسب للتحليلات الكبيرة

### 2. Redis — التجميع الفوري

- **الغرض**: الحفاظ على قائمة المحتوى الأكثر تفاعلاً في آخر 10 دقائق
- **التصميم**: 
  - استخدام Sorted Sets في Redis
  - تجميع الأحداث في "دلاء دقيقة" (minute buckets)
  - كل دقيقة لها مفتاح منفصل (مثل: `zset:top:2025-01-01T12:34+00:00`)
  - النقاط (score) = `engagement_seconds` إن وجدت، وإلا 1
  - انتهاء صلاحية كل دلو بعد 11 دقيقة
- **الهدف**: تحديث خلال أقل من 5 ثوانٍ من استقبال الحدث

### 3. External API — التكامل الخارجي

- **الغرض**: إرسال البيانات المعالجة إلى أنظمة خارجية
- **التنفيذ**: خدمة FastAPI بسيطة تستقبل POST requests
- **معالجة الأخطاء**:
  - إعادة المحاولة مع تأخير متزايد (exponential backoff)
  - حتى 5 محاولات
  - في حالة الفشل الدائم: حفظ الحدث في ملف "dead letter" للمراجعة لاحقاً

## لماذا ClickHouse بدل BigQuery؟

المشروع يستخدم **ClickHouse** كبديل محلي لـ BigQuery لسبب بسيط: عدم توفر بيانات اعتماد GCP (Google Cloud Platform).

ClickHouse يوفر:
- نفس الغرض التحليلي (تخزين عمودي سريع)
- استعلامات SQL قوية
- أداء ممتاز للتجميعات والتحليلات
- قابلية التشغيل محلياً بدون تكاليف سحابية

جميع الأمثلة والاستعلامات التي كانت ستُكتب لـ BigQuery تُكتب هنا لـ ClickHouse بنفس الطريقة.

## واجهة المراقبة (Pipeline Observer UI)

تم إضافة واجهة ويب بسيطة وقراءة فقط لعرض حالة الـ pipeline بصرياً.

### الغرض:
- التحقق البصري من أن البيانات تتدفق بشكل صحيح
- عرض الأرقام الرئيسية (عدد الأحداث في ClickHouse، عدد دلاء Redis)
- عرض المحتوى الأكثر تفاعلاً من آخر دقيقة
- رسم تخطيطي بسيط لتدفق البيانات

### الوصول:
افتح `http://localhost:8080` في المتصفح بعد تشغيل المشروع.

الواجهة تتحدث تلقائياً كل 5 ثوانٍ لعرض البيانات الحية.

### ملاحظات التصميم:
الواجهة **مصممة عمداً لتكون بسيطة وقراءة فقط**، بهدف التحقق البصري من سلوك الـ pipeline بدون الحاجة إلى استخدام سطر الأوامر. إنها أداة للتحقق السريع والعرض التوضيحي، تركز على الوضوح والأناقة التحريرية بدلاً من لوحات معلومات معقدة.

---

## إعادة معالجة البيانات (Backfill)

في بعض الحالات، قد تحتاج إلى إعادة معالجة بيانات تاريخية (مثلاً: بعد إصلاح خطأ في المعالجة، أو لإضافة بيانات قديمة إلى النظام).

### الأداة:
يوجد أداة CLI مخصصة (`scripts/backfill.py`) يمكنها قراءة الأحداث من PostgreSQL وإرسالها إلى Kafka.

### طريقتان للاستخدام:

**1. حسب نطاق المعرفات (ID Range)**:
```bash
python backfill.py --id-range 1 1000
```

**2. حسب نطاق الوقت (Timestamp Range)**:
```bash
python backfill.py --ts-range 2025-01-01T00:00:00 2025-01-01T01:00:00
```

بعد إرسال البيانات إلى Kafka، يقوم المعالج تلقائياً بمعالجتها وإرسالها إلى الوجهات الثلاث، تماماً كما يحدث مع البيانات الجديدة.

## التشغيل السريع

لتشغيل المشروع بالكامل:

```bash
docker compose up -d --build
```

هذا الأمر يقوم بـ:
- بناء جميع الصور المطلوبة
- تشغيل جميع الخدمات (PostgreSQL, Kafka, Redis, ClickHouse, إلخ)
- بدء توليد البيانات تلقائياً
- بدء المعالجة والتوزيع

انتظر دقيقة تقريباً حتى تصبح جميع الخدمات جاهزة وتبدأ البيانات بالتدفق.

بعد ذلك، يمكنك:
- فتح `http://localhost:8080` لرؤية واجهة المراقبة
- فتح `http://localhost:8123` للوصول إلى ClickHouse
- فحص سجلات المعالج: `docker compose logs -f processor`

## ملاحظات ختامية

### فلسفة التصميم

هذا المشروع يفضل **البساطة والوضوح** على التعقيد غير الضروري. الهدف هو بناء نظام:
- **واضح**: يمكن فهمه بسهولة
- **عملي**: يعمل بشكل صحيح في بيئة محلية
- **قابل للتفسير**: كل جزء له سبب واضح

### الاختيارات التقنية

- **Faust**: اختيار مناسب لفريق يعمل بـ Python، رغم وجود بدائل أقوى للإنتاج (مثل Flink أو Spark)
- **معالجة الأخطاء**: نهج عملي يركز على المرونة والمراقبة بدلاً من ضمانات معقدة
- **التوثيق**: كل قرار موثق وموضح

### للبيئة الإنتاجية

في بيئة إنتاجية حقيقية، قد ترغب في:
- استخدام Flink أو Spark Structured Streaming لضمانات أقوى
- إضافة Schema Registry لإدارة تطور البيانات
- تحسين استراتيجية الإثراء (مثل: cache محلي)
- استخدام ReplacingMergeTree في ClickHouse لإزالة التكرارات

لكن لهذا المشروع، البساطة والوضوح هما الأولوية.
